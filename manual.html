01

總覽

Endex eBike Monitor 是一支給研發／產線工程師使用的診斷工具：瀏覽器透過 Web Bluetooth 連上車輛的 BLE↔CAN 橋接模組，用來排查故障、驗證韌體行為、採集騎乘資料。

即時 CAN 輪詢

以 Tool_R 封包逐筆送出請求，控制器非同步回覆，介面即時更新速度、電流、電壓、暫存器等數值。

高頻批次記錄

切換至記錄模式後，控制器改送固定週期的批次封包，適合採集高取樣率資料供事後分析。

暫存器位元檢視

Fault／Status／Peripheral／電池暫存器逐 bit 拆解，紅燈代表異常、綠燈代表正常運作中。

本專案沒有建置流程、套件管理或自動測試——沒有模擬裝置，驗證方式就是連上真實硬體實際操作。
02

啟動環境

Web Bluetooth 只在「安全情境」下可用：localhost 或 HTTPS。直接用 file:// 開啟 index.html 無法呼叫藍牙 API。

方式指令備註
npx servenpx serve .任意 Node 環境皆可，免安裝
Pythonpython -m http.server 8080需系統已裝 Python

啟動後以瀏覽器開啟 http://localhost:8080。瀏覽器需為 Chrome 或 Edge（支援 Web Bluetooth API），且電腦藍牙需已開啟並在裝置有效範圍內。

03

連線 BLE

頁面左上角是唯一的連線入口，連線／中斷共用同一顆按鈕。

操作步驟

  1. 按下 BLE 連線，系統彈出裝置選單，選擇目標車輛。
  2. 連線成功後按鈕變為 關閉連線，狀態燈由灰轉綠， 旁邊顯示裝置名稱與偵測到的 UART Profile（如 NUS）。
  3. 應用程式會依序嘗試 ESP_GATTS → NUS → HM10 → SPP，取第一組同時具備 Write／Notify 特徵值的 Service，不需手動選擇 Profile。
  4. NUS Profile 若帶有 Config 特徵值，連線時會自動送出 5-byte 封包設定鮑率（預設 460800）。
  5. 需要中斷時再按一次同一顆按鈕，或直接關閉裝置電源／拉開距離觸發斷線。

裝置選單：如何挑對裝置

程式以 acceptAllDevices: true 呼叫 requestDevice()，不會用 Service UUID 預先過濾，所以選單會列出當下所有掃描到（含系統已配對）的藍牙裝置，不只是車輛本身。在 Windows 上這會是系統層級的 藍牙配對視窗（標題列顯示發出請求的來源，例如 localhost:8080 想要配對），而不是 Chrome 分頁內的清單；macOS／Linux 則會看到 Chrome 自帶的分頁內選單，行為一致，外觀不同。

  • 認裝置名稱，不要認順序——控制器的 BLE 廣播名稱固定為 ENDEX_CAN_XXXX 格式（XXXX 為該顆控制器的識別碼），附近若有其他藍牙裝置同時在列，順序不保證固定。
  • 「已配對」不代表選錯——標示已配對的裝置是系統先前握手過的紀錄，一樣可以直接點選繼續連線，不需要先取消配對。
  • 灰底「未知或不支援的裝置」多半可以忽略——這類項目通常是系統偵測到訊號但拿不到裝置名稱的周邊（滑鼠、耳機等），除非確定車輛控制器沒有廣播名稱，否則不會是要選的項目。
斷線會自動停止：強制啟動監控、向量監控、記錄模式在偵測到 gattserverdisconnected 時都會自動停止並重置按鈕狀態，不需要手動清理。

功能鍵面板

連線列下方是可折疊的功能鍵面板，收合後畫面更精簡，展開後可調整 StartCmd 全參數與各項監控開關。

▶ 強制啟動 與 ▶ 向量監控 是「模擬上表」的功能： 正常情況下 StartCmd （餵狗＋助力／燈光／模式等控制指令，見第 05 節）是由車輛的上表（把手顯示器／儀表）持續送給馬達控制器的。 這兩顆按鈕讓這支工具直接從電腦代送同一份 StartCmd，等於軟體模擬了一顆上表——即使控制器沒有接上實體上表， 也能單獨用這支工具啟動並監控控制器，不必為了讀資料另外接一顆上表當「開機鑰匙」。
控制項行為
▾ / ▸ 功能鍵收合／展開下方 StartCmd 參數列與 Tick 項目列，畫面空間有限時可先收起
助行勾選即在 StartCmd 的 D1 送出 0xA5（Push Assist 開），取消則送 0x00

⏺ 開始記錄切換韌體進入／退出記錄模式（詳見第 10 節），與 CAN 輪詢互斥
📖 操作說明書開啟隨專案附帶的 manual.html（新分頁），不需連線、不需帳號即可使用

「強制啟動」與「向量監控」按鈕在未連線時點擊會跳出提示要求先連線；記錄模式開啟期間， 兩者會被停用（灰階、無法點擊），因為控制器此時已停止回覆 Tool_R 封包。

05

StartCmd 參數

StartCmd 是唯一同時「餵狗」（維持控制器 watchdog）又「下指令」（燈光、模式、排檔…）的封包， 只要監控迴圈在跑就必須每輪送出，否則控制器可能判定連線逾時。8 個資料位元組（D0–D7）對應下列參數列：

位元組名稱數值 / 位元定義
D0助力等級 Assist Level0 ~ 5（bits 2:0）
D1助行 Push Assist0x00 關 / 0xA5 開（沿用頂列「助行」勾選框）
D2燈光 Lightbit0 前燈・bit1 後燈・bit2 左燈・bit3 右燈
D3開關 Switch0x00 Idle / 0x5A Power On / 0xA5 Power Off
D4操作模式 Operation0x00 Normal / 0x5A Boost / 0xEC Eco / 0xEA Easy / 0xAE Navi / 0xA5 Locked
D5Driver 廣播 Broadcast0 Disable / 1 Enable / 2 Mute
D6電池鎖 Battery Lock0x5A Unlocked / 0x00 Locked
D7排檔 Gearbits 3:0 檔位 0~15・bit5(0x20) 升檔・bit6(0x40) 降檔

修改任一控制項，列尾的 D0:xx D1:xx … 預覽會即時更新，方便下手前先確認實際送出的 hex 值。

全域接收統計

All RX 累計自連線以來收到的全部 Tool_R 封包數，並即時估算平均與最短間隔（取樣最近 10 筆），可用來粗估控制器實際回覆頻率或發現丟包。

記錄批次計數

記錄模式開啟後，「車輛」「馬達」兩顆計數器分別累加已收到的批次數；旁邊的 匯出車輛 CSV / 匯出馬達 CSV 可隨時手動匯出目前緩衝，「自動儲存」勾選框與間隔設定見第 10 節。

09

電池資訊

按 🔋 電池資訊 開啟彈窗，內容分成兩欄（電池1／電池2）， 每欄再各自區分兩種資料來源：

CAN 輪詢（即時）

Voltage／Current／Temp／RSOC／ASOC／SOH／Full Charge／Remain Cap，以及 13-bit Fault Register 與 8-bit Status Register——控制器週期性主動廣播，不需要送請求，單電池車型會改用 Single Battery 專用 CAN ID 廣播同一組欄位。

記錄模式（批次）

RSOC／Temp／Status／16-bit Fault（bit0~12 定義與 CAN 版相同，bit13~15 保留）， 取自記錄批次的對應欄位；頂部另有「模擬 SOC」（SimualRSOC）只在記錄模式下有值。

兩種來源指向同一顆實體電池、同一個暫存器定義，只是走不同傳輸路徑——在記錄模式尚未收到任何批次前， 「記錄模式」欄位會顯示 —。

10

記錄模式

記錄模式讓控制器切換成高頻批次輸出，取樣密度遠高於逐筆 CAN 輪詢，適合做波形分析、 事件重現。開啟時會自動停止 CAN 輪詢與向量監控，因為兩種格式互斥、無法同時解析。

開始 / 停止

  1. 按 ⏺ 開始記錄：立即凍結目前卡片數值作為「記錄前基準」， 送出開啟指令後切換解析格式，按鈕變為 ⏹ 停止記錄。
  2. 「強制啟動」「向量監控」按鈕在記錄期間停用；記錄批次計數器（第 06 節）開始累加。
  3. 再按一次按鈕即送出關閉指令、切回 CAN 輪詢解析格式，按鈕與其餘功能鍵恢復可用。

Debug 面板

主畫面下方兩個 Debug 方塊分別顯示「車輛狀態批次」與「馬達 Id/Iq 批次」最新收到的一筆原始 bytes（HEX）與解析後欄位，用來直接核對協定是否解析正確，不需要另外接封包擷取工具。

記錄前 CAN 基準 vs 記錄中最新值

比對表把「進入記錄模式那一刻」凍結的 CAN 數值，跟記錄批次持續更新的最新值並排顯示，數值不同的列會標色， 方便肉眼確認兩種資料來源是否一致。前述 Total Assist／Single Trip／Remain Dist 三個欄位協定裡沒有對應資料，因此刻意不列入比對表。

疑難排解

依嚴重度排序，先處理連不上線的問題，再處理資料解析異常。

按下「BLE 連線」沒有反應，或跳出安全情境錯誤
原因Web Bluetooth 需要安全情境，用 file:// 直接開啟 index.html 不符合條件。
處理改用 npx serve . 或 python -m http.server 起本機伺服器，改用 http://localhost:port 開啟，並確認瀏覽器是 Chrome 或 Edge。
選到裝置後跳出「無法自動偵測 BLE UART Characteristics」
原因依序嘗試 ESP_GATTS／NUS／HM10／SPP 四組 Profile 都找不到同時具備 Write + Notify 的 Service。
處理確認選到的是正確裝置（非附近其他藍牙裝置）、韌體有正確廣播對應 Service UUID；錯誤訊息裡會列出每個 Profile 各自失敗的原因，可據此比對第 12 節的 UART Profile 對照表。
強制啟動已開啟，但卡片數值一直不動
原因對應的 Tick 項目（Fault／Status／Assist／Distance／Motor Vec）沒有勾選，該類請求就不會送出。
處理回到第 06 節勾選需要的項目；若 Start 也被取消勾選，控制器可能因收不到餵狗封包而斷開，建議 Start 保持常駐勾選。
記錄模式 Debug 面板一直顯示「尚未收到資料」，或解析數值明顯異常
原因記錄批次沒有 magic byte 可以重新對齊，一旦切幀長度判斷錯誤，緩衝區就會永久錯位，後續所有批次都讀到偏移過的資料。
處理先確認是否為已知修正過的切幀問題（車輛與馬達批次總長度不同，需依各自的 length byte 動態切幀，不可假設固定長度）；若持續發生，重新開關一次記錄模式讓緩衝重置，或中斷 BLE 連線重連。
找不到自動儲存匯出的 CSV 檔案
原因匯出使用瀏覽器原生下載，不是寫入專案資料夾。
處理檢查瀏覽器的下載設定（Chrome：chrome://settings/downloads）確認預設下載資料夾，或是否設成每次下載詢問位置。

Recording Mode 批次封包

以 0xFD 開關（手機 → 裝置），開啟後裝置改送 command(1) + length(1) + payload(length) 的批次，兩種批次型別總長度並不相同：

0xFD 車輛狀態批次

總長 212 bytes（payload 210 bytes）= 6 筆 × 35 bytes：速度、電流、電壓、Fault/Status/Peripheral 暫存器、踏頻、電池 RSOC/Status/Temp 等。

0xFE 馬達 Id/Iq 批次

總長 242 bytes（payload 240 bytes）= 24 筆 × 10 bytes：計數、轉子角度、Id、Iq、Vd_cmd、Vq_cmd。

切幀依 length byte 動態決定，不可假設固定長度： REC_CMD_BYTE（手機→裝置的開關指令） 與 REC_BATCH_VEHICLE（裝置→手機的車輛批次標籤）數值同為 0xFD，方向相反、意義不同， 追封包時務必留意。此格式沒有 magic byte 可重新對齊，一旦誤判某筆長度，後續所有批次會永久錯位。
